# Dota 2 — дизайн-документ (практичні заняття 15–16)

## 1. Призначення та межі проєкту

Dota 2 — навчальний застосунок на C# / .NET 8 із консольним і графічним інтерфейсами. Він містить каталог персонажів Dota 2, імпорт JSON з OpenDota API та покрокову бойову гру. Графічна оболонка для Windows реалізована окремим проєктом Windows Forms. Це прототип бізнес-компоненти, а не симулятор усіх правил оригінальної Dota 2.

Для каталогу використано альтернативне джерело `https://api.opendota.com/api/heroes`, що дозволено умовою практичної роботи. API повертає основні відомості про героїв. Бойові характеристики, яких немає у відповіді цього endpoint, задаються тестовими значеннями.

## 2. Архітектура та розділення відповідальності

Проєкт розділений на бізнес-ядро, інфраструктурні адаптери та консольний інтерфейс.

- **Core/Hero.cs** — модель персонажа та нейтральна `HeroCardData` для передачі даних компоненту GUI. Модель не залежить від CLI, HTTP чи файлової системи.
- **Core/Contracts.cs** — абстракції `IHeroLookup`, `IHeroCatalog`, `IHeroRepository`, `IGameStateRepository`, `IGameResultRepository`, `IHeroApiClient`. Ядро залежить від контрактів, а не від конкретних адаптерів.
- **Core/HeroCatalog.cs** — керує каталогом, пошуком, додаванням та оновленням персонажів. Він не виконує HTTP-запитів і не знає формату JSON-файлу.
- **Core/BattleGame.cs** — правила бою, математичні обчислення, запуск/завантаження гри, обробка дій, перемога та історія. Клас використовує тільки інтерфейси.
- **Core/BattleTurn.cs** — окремий об'єкт раунду. Формує впорядковану послідовність дій за швидкістю.
- **Core/GameState.cs** — серіалізований стан бою та журнал `TurnRecord`.
- **Data/OpenDotaHeroApiClient.cs** — інфраструктура HTTP та парсинг JSON у моделі `Hero`.
- **Data/JsonDataStore.cs** — файловий адаптер для каталогу, стану гри та результатів. Реалізує репозиторні інтерфейси.
- **Cli/** — адаптер командного рядка. Команди передають запити до бізнес-класів і не містять формул бою.
- **Program.cs** — composition root: створює адаптери та передає їх через конструктори (ручний Dependency Injection).

Схема залежностей:

```text
CLI -> HeroCatalog
HeroCatalog -> IHeroRepository <- JsonDataStore
HeroCatalog -> IHeroApiClient <- OpenDotaHeroApiClient
CLI -> BattleGame
BattleGame -> IHeroLookup <- HeroCatalog
BattleGame -> IGameStateRepository <- JsonDataStore
BattleGame -> IGameResultRepository <- JsonDataStore
GUI/MainForm -> HeroCatalog -> HeroCardData
```

`HeroCatalog` реалізує `IHeroCatalog` і формує нейтральні об'єкти `HeroCardData` для карток. Бізнес-логіку можна тестувати з фіктивним каталогом і сховищем, не звертаючись до мережі чи диска.

## 3. Каталог персонажів і JSON-парсинг

Команда `refresh` викликає `HeroCatalog.RefreshAsync()`. Каталог отримує вже перетворені моделі від `IHeroApiClient`; поточна реалізація адаптера надсилає HTTP GET до OpenDota API.

`OpenDotaHeroApiClient` читає відповідь за допомогою `JsonDocument` та перевіряє, що кореневий JSON-елемент є масивом. Для кожного об'єкта зчитуються:

- `name` — внутрішній ID API;
- `localized_name` — ім'я для показу;
- `primary_attr` — атрибут (`str`, `agi`, `int`, `all`);
- `attack_type` — тип атаки.

Префікс `npc_dota_hero_` прибирається з ID, а символ `_` замінюється на `-`. Некоректні елементи без ID або імені пропускаються. Значення атрибута перетворюється на зрозумілий рядок. Для ілюстрації GUI формується `ArtworkUrl`. `HeroCardData` містить ID, ім'я, атрибут, тип атаки, зображення та бойові показники — дані, яких достатньо для побудови ViewModel картки персонажа.

API endpoint не надає HP, Attack, Armor, Resist та Speed. Тому для них явно встановлюються навчальні тестові значення: HP=100, Attack=15, Armor=5, Resist=0.10, Speed=100. Це не видається за офіційні характеристики гри.

Оновлення каталогу виконується без втрати старого стану: спочатку завантажується і перевіряється новий список, потім до нього додаються локальні персонажі, які не дублюють API, далі список записується у сховище і лише після успішного запису замінює поточну колекцію.

## 4. Модель персонажа

| Поле | Значення |
|---|---|
| `Id`, `Name` | Унікальний ідентифікатор та ім'я |
| `Attribute`, `AttackType` | Основний атрибут і тип атаки з API |
| `MaxHp` | Максимальне здоров'я, ціле число більше 0 |
| `Attack` | Базова сила атаки, не менше 0 |
| `Armor` | Плоский захист, не менше 0 |
| `Resist` | Частка шкоди, що ігнорується, від 0 до 1 |
| `Speed` | Швидкість, більше 0; визначає кількість та порядок дій |
| `ArtworkUrl` | URL зображення |
| `Description` | Опис для інтерфейсу |

Під час створення персонажа та імпорту перевіряються обмеження характеристик. На початку бою профілі персонажів копіюються у `GameState`. Отже, зміна каталогу після початку бою не змінює характеристики вже запущеного матчу.

## 5. Математика та правила бою

У кожного учасника є характеристики:

- **Health (HP)** — поточне здоров'я;
- **MaxHp** — максимальне здоров'я;
- **Attack** — сила атаки;
- **Armor** — плоский захист;
- **Resist** — частка шкоди, яку персонаж ігнорує;
- **Speed** — швидкість, яка визначає кількість та порядок дій за раунд.

Загальні обмеження: `0 <= HP <= MaxHp`, `Attack >= 0`, `Armor >= 0`, `0 <= Resist <= 1`, `Speed > 0`.

### 5.1. Фізична шкода

Спочатку з атаки віднімається броня, від'ємний результат замінюється нулем. Потім застосовується опір цілі:

```text
Damage = floor(max(0, Attack - Armor) * (1 - clamp(Resist, 0, 1)))
```

`clamp` обмежує Resist діапазоном 0..1, `floor` округлює результат униз до цілого числа. Броня повністю блокує атаку, якщо `Attack <= Armor`.

Приклад: Attack=30, Armor=10, Resist=0.25:

```text
Damage = floor(max(0, 30 - 10) * (1 - 0.25))
Damage = floor(20 * 0.75) = 15
```

У цій версії всі базові атаки використовують цю фізичну формулу. Магічна шкода, пробиття опору, бонуси предметів/навичок, buffs і debuffs не входять до обсягу реалізованої версії; їх можна додати окремими типами шкоди та модифікаторами.

### 5.2. Дії

- **attack** — атакує суперника. HP цілі зменшується на розраховану шкоду, але не опускається нижче 0.
- **heal** — відновлює 20 HP: `NewHP = min(MaxHp, CurrentHP + 20)`. Персонаж не може бути воскресений після завершення бою.
- **defend** — встановлює прапорець захисту. Наступна отримана атака зменшується вдвічі: `BlockedDamage = floor(Damage * 0.5)`. Після одного отриманого удару захист споживається.
- **status** — показує стан, не витрачає дію та не просуває раунд.

Після кожної дії гравця суперник виконує автоматичну атаку згідно зі своєю позицією в розкладі раунду. Якщо HP будь-якого учасника дорівнює 0, бій завершується негайно і решта запланованих дій скасовується.

### 5.3. Швидкість і порядок дій

За правилом методички швидкість визначає і кількість, і послідовність дій. Для швидкості `S` кількість дій за раунд:

```text
ActionCount = max(1, floor(S / 100))
```

Часова позиція кожної дії всередині умовного раунду:

```text
ActionTime(k) = (k * 100) / S, де k = 1..ActionCount
```

Усі дії обох персонажів об'єднуються в одну чергу та сортуються за `ActionTime` за зростанням. Якщо часові позиції однакові, першою діє персонаж із більшою Speed; якщо швидкості однакові — спочатку гравець. Це дає таку поведінку, як у прикладах методички:

| Speed | Дії за раунд | Порядок у прикладі |
|---:|---:|---|
| 100 | 1 | одна дія наприкінці базового інтервалу |
| 150 | 1 | дія раніше за персонажа зі Speed 100 |
| 200 | 2 | перша дія на позиції 0.5, друга на позиції 1.0 |

Приклад для учасників зі швидкістю 200, 150 та 100: дія персонажа зі Speed 200 відбувається на 0.5; дія зі Speed 150 — на 0.667; друга дія зі Speed 200 — на 1.0 і за правилом розв'язання нічиєї передує Speed 100; дія зі Speed 100 завершує інтервал. Таким чином персонаж зі Speed 200 отримує додаткову дію всередині раунду, а персонаж зі Speed 150 діє раніше за Speed 100.

У поточній грі два учасники. Команда гравця (`attack`, `heal` або `defend`) застосовується до кожної дії гравця в розкладі раунду; автоматична дія суперника завжди є атакою. Це дозволяє одному `act` завершити повний раунд і коректно відобразити додаткові дії швидкого персонажа.

### 5.4. Завершення бою

Після кожної дії перевіряється HP. Якщо HP гравця дорівнює 0, перемагає суперник; якщо HP суперника дорівнює 0, перемагає гравець. Результат фіксується один раз у `game-results.txt`, стан позначається як завершений, подальші дії заборонені.

## 6. Раунди та історія

Клас `BattleTurn` формує незмінний список `ScheduledAction` для одного раунду. `BattleGame` виконує його по черзі. Кожна фактично виконана дія додається в `TurnRecord` із номером раунду, порядковим номером дії, виконавцем, назвою дії, фактичною шкодою/лікуванням, повідомленням і часовою міткою.

Історія зберігається в `GameState.History`. Команда `history` показує всі записи в хронологічному порядку. Оскільки записи мають номер раунду та послідовність, можна відтворити порядок дій, включно з додатковими діями за Speed=200.

## 7. Постійність інформації: збереження та завантаження (практичне заняття 15)

Для цієї практичної роботи я реалізував варіант «Текстова гра». Я використав постійну пам’ять у вигляді локальних файлів JSON, щоб після завершення програми користувацькі дані не втрачалися. Об’єкти C# я перетворюю на текстове представлення за допомогою серіалізації `System.Text.Json`, а під час наступного запуску відновлюю їх десеріалізацією.

Я зберігаю файли у системній директорії користувача `AppData/Local/Dota2CLI` (у Windows шлях відповідає `%LOCALAPPDATA%\Dota2CLI`). Таким чином, файли даних не потрапляють до папки з виконуваним файлом і не змішуються з файлами проєкту.

Я використовую три файли:

- `heroes.json` — повний каталог стандартних і створених мною персонажів. Після виконання команди `create` новий персонаж одразу записується до цього файлу, тому залишається доступним після закриття та повторного запуску програми.
- `game-state.json` — останній стан бою. Я зберігаю ID учасників, копії їхніх бойових профілів, поточне HP, номер раунду, прапорець захисту, ознаку завершення, результат та історію дій із часовими мітками.
- `game-results.txt` — журнал результатів завершених боїв.

**Як я зберігаю дані.** Коли я створюю персонажа, `HeroCatalog` передає оновлений каталог у `JsonDataStore`, який серіалізує його у `heroes.json`. Коли я починаю бій або виконую команду `act`, `BattleGame` оновлює об’єкт `GameState` та передає його до `JsonDataStore`. Стан автоматично зберігається після початку бою та після кожного повного раунду. За потреби я можу додатково виконати команду `save`.

Щоб зменшити ризик втрати останнього збереження під час переривання запису, я спочатку створюю окремий тимчасовий файл із унікальним суфіксом `.tmp`, записую до нього JSON, а потім замінюю ним основний файл. Тимчасовий файл видаляється після завершення операції.

**Як я відновлюю дані.** Під час запуску програма перевіряє, чи існує `game-state.json`. Якщо файл знайдено, програма автоматично завантажує останній збережений бій. Я можу також виконати команду `load`, щоб повторно завантажити останнє збереження вручну. Після відновлення я бачу попередні значення HP, номер раунду, учасників та історію і можу продовжити гру наступною командою `act`.

Я зберігаю копії профілів обох учасників безпосередньо в `GameState`. Завдяки цьому вже розпочатий бій не залежить від подальшого оновлення каталогу або доступності OpenDota API. Створені мною персонажі зберігаються в `heroes.json` з ознакою `IsUserCreated` і залишаються доступними для наступних боїв. Під час оновлення каталогу з API ця ознака дає змогу зберегти моїх персонажів навіть тоді, коли їхні ID або імена збігаються з даними сервера. Водночас звичайні записи каталогу можуть оновлюватися свіжими даними API.

Під час завантаження я перевіряю наявність ID учасників, коректність характеристик профілів, відповідність ID, межі HP, номер раунду, результат та записи історії. Якщо JSON пошкоджений або його дані логічно некоректні, програма повідомляє про помилку та не відновлює такий стан як справний. Для каталогу я також перевіряю порожні записи, коректність характеристик і повторювані ID.

**Послідовність роботи:**

```text
Команда create
    -> HeroCatalog
    -> JSON-серіалізація
    -> AppData/Local/Dota2CLI/heroes.json

Команда play
    -> створення GameState
    -> JSON-серіалізація
    -> AppData/Local/Dota2CLI/game-state.json

Команда act
    -> виконання повного раунду
    -> оновлення GameState та історії
    -> автоматичне збереження JSON

Наступний запуск програми
    -> перевірка game-state.json
    -> JSON-десеріалізація
    -> перевірка даних
    -> відновлення останнього бою
    -> продовження гри
```

Таким чином, я реалізував обидві частини вимоги практичної роботи для текстової гри: збереження стану та створених користувачем персонажів, а також відновлення останнього збереження з можливістю продовжити гру після повторного запуску.

## 8. Команди CLI

| Команда | Призначення |
|---|---|
| `help` | Довідка |
| `refresh` | Завантажити актуальний каталог з OpenDota API |
| `heroes` | Показати каталог |
| `hero <id або ім'я>` | Показати профіль персонажа |

| `create` | Створити локального персонажа |
| `play <id1> <id2>` або `play` | Почати бій |
| `act attack` | Атакувати в кожній дії гравця поточного раунду |
| `act heal` | Лікуватися в кожній дії гравця поточного раунду |
| `act defend` | Активувати захист у кожній дії гравця поточного раунду |

| `history` | Показати журнал усіх дій |
| `save` | Зберегти стан |
| `load` | Завантажити останній збережений стан |

| `exit` | Завершити програму |

## 10. Обмеження

Це навчальна покрокова гра з двома учасниками й автоматичним AI-суперником. Вона не відтворює повну Dota 2. Усі API-імпортовані герої отримують тестові бойові значення, оскільки endpoint каталогу не містить потрібних бойових параметрів. Для графічного інтерфейсу використовується нейтральна модель `HeroCardData`, яку `HeroCatalog.GetCards()` передає формі. Вона відокремлює дані картки від конкретної реалізації інтерфейсу.

## 12. Графічний інтерфейс (практичне заняття 16)

Для графічної оболонки використано **Windows Forms для .NET 8 (C#)**. Це нативний настільний інтерфейс Windows. GUI винесено в окремий проєкт `Gui/Dota2GUI.csproj`, який посилається на основний `Dota2CLI.csproj`. Завдяки цьому консольний застосунок і попередні автоматизовані тести залишаються окремими та не залежать від Windows Forms.

### 12.1. Екрани та елементи

Головне вікно містить дві вкладки:

1. **«Каталог персонажів»**
   - прокручувана панель карток `FlowLayoutPanel`;
   - картка кожного героя містить портрет `PictureBox`, ім'я та короткі характеристики: атрибут, тип атаки, HP, атаку, броню, опір і швидкість;
   - зображення завантажується за `ArtworkUrl`, отриманим із каталогу;
   - під час запуску застосунок автоматично намагається оновити каталог через OpenDota API; кнопка «Оновити каталог» дає змогу повторити запит;
   - після оновлення картки та списки вибору персонажів перемальовуються.

2. **«Бойова гра»**
   - два списки `ComboBox` для вибору гравця та суперника;
   - кнопка «Почати бій» створює новий стан через `BattleGame.Start`;
   - кнопки «Атакувати», «Лікуватися» та «Захищатися» викликають `BattleGame.Act`;
   - кнопки «Стан бою» та «Історія» виводять дані з бізнес-логіки;
   - темне багаторядкове поле `RichTextBox` відображає повідомлення та події гри й автоматично прокручується до останнього запису;
   - кнопка «Зберегти як…» експортує поточний стан у JSON-файл;
   - кнопка «Вибрати та завантажити сейв…» відкриває діалог вибору JSON-файлу, передає стан наявному сховищу та відновлює його через `BattleGame.Load`.

### 12.2. Архітектура та взаємодія

`MainForm` відповідає за відображення елементів і обробку подій кнопок. Він не реалізує правила бою та не дублює роботу з OpenDota API. Для цього використовуються наявні класи `HeroCatalog`, `BattleGame`, `OpenDotaHeroApiClient` і `JsonDataStore`.

```text
Gui/MainForm
   |-- HeroCatalog ---------------- OpenDotaHeroApiClient
   |       |                       (HTTP / OpenDota API)
   |       |
   |       +----------------------- JsonDataStore
   |
   +-- BattleGame ----------------- HeroCatalog
           |
           +---------------------- JsonDataStore
```

Застосовано подієву модель Windows Forms: натискання кнопок запускає відповідні обробники подій. Операція оновлення каталогу виконується асинхронно, щоб не блокувати вікно на час HTTP-запиту. Зміни стану бою зберігаються наявною логікою `BattleGame`, а вибрані користувачем файли збережень читаються та перевіряються через `BattleGame.Load`. Під час запуску спочатку відображається локальний каталог, після чого застосунок асинхронно оновлює його з OpenDota API. Якщо мережа недоступна або API повертає помилку, локальний каталог залишається доступним.

- Створення першого застосунку Windows Forms: https://learn.microsoft.com/dotnet/desktop/winforms/get-started/create-app-visual-studio

### 12.4. Запуск графічного застосунку

У Windows із встановленим .NET 8 SDK у кореневій папці проєкту:

```bash
dotnet restore Gui/Dota2GUI.csproj
dotnet run --project Gui/Dota2GUI.csproj
```

Консольний варіант і тести залишаються доступними окремо:

```bash
dotnet run
dotnet run --project Tests/Dota2CLI.Tests.csproj
```

GUI використовує ту саму системну папку даних `%LOCALAPPDATA%\\Dota2CLI`, тому каталог персонажів і останній стан гри спільні для консольної та графічної версій.


## 13. Збирання та розгортання (практичне заняття 17)

Для доставки підготовлено PowerShell-скрипт `build-release.ps1`. Він збирає два виконувані варіанти для Windows x64: графічний Windows Forms застосунок і консольну версію. Перед публікацією скрипт відновлює NuGet-залежності та запускає автоматизовані тести. Якщо тести або будь-який етап публікації завершуються помилкою, скрипт зупиняється.

### 13.1. Параметри публікації

Використовується конфігурація `Release`, runtime identifier `win-x64`, параметр `--self-contained true` та `PublishSingleFile=true`. Отже, застосунок публікується як один основний EXE-файл із потрібними компонентами .NET; користувачу не потрібно встановлювати .NET Runtime окремо. Для GUI потрібна Windows x64. Пакет не є інсталятором.

### 13.2. Залежності для розробника / збірки

- Windows 10 або Windows 11 x64.
- PowerShell 5.1 або новіший.
- .NET 8 SDK (саме SDK, не лише Runtime).
- Доступ до інтернету під час `dotnet restore` і завантаження .NET runtime pack для self-contained публікації; для оновлення каталогу героїв потрібен доступ до OpenDota API.
- Сторонні NuGet-пакети для основних проєктів не використовуються; залежності платформи та .NET обробляються SDK.

### 13.3. Команда збірки

У PowerShell з кореневої папки репозиторію:

```powershell
powershell -ExecutionPolicy Bypass -File .\build-release.ps1
```

Скрипт перевіряє наявність .NET 8 SDK, виконує `dotnet restore`, запускає `Tests/Dota2CLI.Tests.csproj` у Release та публікує GUI і CLI. Якщо залежності, тести або публікація завершуються помилкою, процес зупиняється; перед архівацією перевіряється наявність обох EXE-файлів. Результати з'являються в `release/Dota2GUI` і `release/Dota2CLI`; у корені створюється архів `Dota2CLI_Project_Windows_x64_Release.zip`.

### 13.4. Запуск кінцевим користувачем

Основний спосіб використання — графічна версія. Користувач розпаковує архів (якщо EXE надано в архіві) та запускає `Dota2GUI.exe` подвійним клацанням. Якщо файл було створено командою `dotnet publish` безпосередньо в папку `publish\\win-x64`, його можна запускати звідти. Графічний інтерфейс і програмна логіка, підключена через посилання на основний проєкт, входять до цієї збірки. Окреме встановлення .NET Runtime не потрібне.

`Dota2CLI.exe` є додатковою консольною версією, якщо вона включена до пакета. Інтернет не є обов'язковим для запуску з локальним каталогом, але потрібен для оновлення каталогу через OpenDota API. Дані програми зберігаються в `%LOCALAPPDATA%\\Dota2CLI`.

Публікація через `win-x64` означає, що цей пакет не призначений для macOS, Linux або Windows ARM64. Для цих платформ потрібно виконати окрему публікацію з відповідним runtime identifier.
